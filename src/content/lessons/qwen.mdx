## 小さな表から、学習済みの表へ

[Embeddingの基礎](../embedding/)では、`nn.Embedding(5, 3)`で作った表を参照しました。ここではQwen3-0.6Bが持つ学習済みの表を使い、**「こんにちは」→ ID 89015 → 1024成分のベクトル**までを実物で確かめます。

Embeddingの数値と表示は2026-10-05、Hidden Stateの観察は2026-10-07に確認しました。Python 3.13.15・PyTorch 2.14.1+cu130・Transformers 5.18.0、下記の固定revisionを**CPU・bfloat16**で読み込んだ結果です。GPUや演算方法の違いで数値の一部が変わることがあります。Embeddingの参照からモデルの1回の計算へ進みます。文章生成や学習は実行しません。

## モデル名・クラス・実物を分ける

[最初のモデル読み込み](../first-generation/)で取得したキャッシュを使います。`local_files_only=True`なので、このコード自体は新しくダウンロードしません。キャッシュがない場合は、先にモデルを取得する手順を実行してください。

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "Qwen/Qwen3-0.6B"
revision = "c1899de289a04d12100db370d81485cdf75e47ca"
tokenizer = AutoTokenizer.from_pretrained(
    model_id, revision=revision, local_files_only=True
)
model = AutoModelForCausalLM.from_pretrained(
    model_id, revision=revision, dtype=torch.bfloat16,
    device_map="cpu", local_files_only=True
)
model.eval()
print("type(model):", type(model))
```

```text
type(model): <class 'transformers.models.qwen3.modeling_qwen3.Qwen3ForCausalLM'>
```

読み込み時には進捗表示も出ます。ここでは最後のprintの結果を掲載しています。

| 名前 | 役割 |
|---|---|
| `Qwen/Qwen3-0.6B` | どの配布モデルの設定・学習済み重みを使うかを指定するリポジトリID |
| `AutoModelForCausalLM` | 設定に合う、次トークン予測用のモデルクラスを選ぶ入口 |
| `Qwen3ForCausalLM` | Qwen3の部品構成と計算方法を実装する具体的なクラス |

クラスはプログラム側の構造・処理、重みは学習で得た数値です。`from_pretrained`の返り値として、その両方を持つ実物を受け取っています。`ForCausalLM`はCausal Language Modeling用、つまり過去のトークンから次を予測する用途を表します。

### 作る・取得する・参照する・使う

共通して扱っているのは、IDとベクトルを対応させる仕組みです。その仕組みに対する操作と返り値を分けます。

| 操作 | 何をするか | 得られるもの |
|---|---|---|
| `nn.Embedding(5, 3)` | サイズを指定して新しく作る | 重み表を持つEmbeddingインスタンス |
| `model.get_input_embeddings()` | モデルの既存の層を取得する | 今回はEmbeddingインスタンス |
| `embedding.weight` | 層が持つ表を参照する | ParameterであるTensor |
| `embedding(ids)` | IDを使って表を引く | 対応するベクトルを並べた新しいTensor |

| 指定 | 行として選ぶもの | 列として選ぶもの |
|---|---|---|


比較するのは、**入力のIDが指した行と、その入力位置の出力ベクトル**です。今回は`output[0, 0]`と`weight[89015]`が対応します。先頭10成分だけを表示していますが、比較は1024成分全体に対して行っています。`allclose`は指定した許容誤差内で近いかを判定する関数です。[allcloseの仕様](https://docs.pytorch.org/docs/2.14/generated/torch.allclose.html)

今回の`no_grad()`は観察時の勾配記録を止めます。`model.eval()`のモード切替とは別です。元の重みを更新する処理は含みません。

## 2次元の表から、なぜ3次元の出力になるか

| 対象 | shape | 何を保持するか |
|---|---|---|
| `embedding.weight` | `[151936, 1024]` | 全行のベクトルを持つ表 |
| `ids` | `[1, 1]` | 1件の入力・1個のID |
| `output` | `[1, 1, 1024]` | その位置に対応する1024成分のベクトル |

表は2次元のままです。出力は、入力の各位置にベクトルを置いた結果なので、入力の軸を残し、末尾に1024の軸が加わります。

```text
入力：  [[89015]]
           ↓ その位置に、ID 89015のベクトルを置く
出力：  [[[0.0140, -0.0510, 0.0308, …1024成分…]]]
```

これは構造を説明する模式表示です。**outputに「IDとベクトルの組」が入るわけではありません。** 入っているのは対応するベクトルで、IDは引く行を指定するために使います。元の`ids`も書き換えられず、整数IDを保持したまま残ります。

### 同じIDでも、入力の形は残る

```python
with torch.no_grad():
    for value in [token_id, [token_id], [[token_id]]]:
        shaped_ids = torch.tensor(value, dtype=torch.long, device=embedding.weight.device)
        shaped_output = embedding(shaped_ids)
        print(list(shaped_ids.shape), "->", list(shaped_output.shape))
        print("同じベクトルか:", torch.allclose(shaped_output.reshape(-1, 1024)[0], direct))
```

```text
[] -> [1024]
同じベクトルか: True
[1] -> [1, 1024]
同じベクトルか: True
[1, 1] -> [1, 1, 1024]
同じベクトルか: True
```

選ぶ行が同じなのでベクトルの数値は同じですが、それを包む軸の構造が違います。`tensor(89015)`はスカラー、`tensor([89015])`は1個のIDの並び、`tensor([[89015]])`は1件・各1個のIDのまとまりです。

形を残すことで、後続の計算でも「どの入力の、何番目のトークンか」を位置から追えます。Embedding層そのものが文章の意味やbatchの役割を判断しているのではなく、入力の構造を保つAPIをモデル側が利用しています。

## EmbeddingからHidden Stateへ

ここまでは`embedding(ids)`で表を引きました。次は**同じ入力文をモデル全体へ渡し、計算途中のTensorを受け取ります。** `model(**inputs)`の中でもEmbeddingが実行されるため、先ほどの`output`をもう一度IDとして渡す必要はありません。

```python
text = "こんにちは、今日はいい天気ですね"
encoded_inputs = tokenizer(text, add_special_tokens=False, return_tensors="pt")
inputs = {
    key: value.to(model.get_input_embeddings().weight.device)
    for key, value in encoded_inputs.items()
}
with torch.no_grad():
    outputs = model(
        **inputs, output_hidden_states=True, use_cache=False
    )
hidden_states = outputs.hidden_states
print("Decoder Layer数:", len(model.model.layers))
print("状態の型:", type(hidden_states))
print("保存された状態の個数:", len(hidden_states))
print("各状態のshape:", hidden_states[0].shape)
print("全状態が同じshapeか:",
      all(h.shape == hidden_states[0].shape for h in hidden_states))
```

```text
Decoder Layer数: 28
状態の型: <class 'tuple'>
保存された状態の個数: 29
各状態のshape: torch.Size([1, 7, 1024])
全状態が同じshapeか: True
```

### 入力の容器と、中のTensorを分ける

`encoded_inputs`はTokenizerから受け取った`BatchEncoding`です。`tokenizer(...)`の時点でID変換まで終わっており、この例では`input_ids`と`attention_mask`がすでにTensorになっています。[Tokenizerの返り値](../tokenizer/)で確認できます。

```text
encoded_inputs：BatchEncoding
├─ "input_ids"      → 整数IDのTensor [1, 7]
└─ "attention_mask" → 有効な位置を示すTensor [1, 7]
                         ↓ 各Tensorを配置先へ合わせる
inputs：通常のdict（同じキーでTensorを保持）
                         ↓ model(**inputs)
outputs：モデルの返り値
└─ hidden_states → 29個のTensorを並べたtuple
```

辞書内包表記で作った`inputs`は、通常の`dict`です。`encoded_inputs`の型が、そのまま新しい辞書へ引き継がれるわけではありません。どちらの容器自体にもTensorのような`device`はなく、中の各Tensorに配置先があります。

`**inputs`は、キーを引数名、値を引数の値として渡します。今回なら`model(input_ids=inputs["input_ids"], attention_mask=inputs["attention_mask"], ...)`という呼び出しに相当します。

| 指定・返り値 | 今回の役割 |
|---|---|
| `output_hidden_states=True` | 中間状態も返すように指定する |
| `use_cache=False` | 今回の観察では生成用のKV cacheを返さない |
| `outputs` | Hidden Stateやlogitsを含むモデルの返り値 |
| `outputs.hidden_states` | 計算の節目にあるTensorを並べたtuple |

`model(...)`はここでは1回のforward計算です。`generate(...)`のようにトークンを選んで追加する処理ではなく、学習済み重みを書き換える処理でもありません。

### 辞書の各Tensorを配置先へ合わせる

上の辞書内包表記を普通のfor文で書くと、次のようになります。どちらか一方を使えば十分です。

```python
device = model.get_input_embeddings().weight.device
expanded_inputs = {}
for key, value in encoded_inputs.items():
    expanded_inputs[key] = value.to(device)
print("同じキーと値か:", expanded_inputs.keys() == inputs.keys()
      and all(torch.equal(expanded_inputs[k], inputs[k]) for k in inputs))
```

```text
同じキーと値か: True
```

`encoded_inputs.items()`はキーと値のペアを順に渡します。`key, value`でそのペアを分けて受け取り、同じキーに`value.to(device)`の返り値を入れます。**deviceという表示だけを書き換えるのではなく、必要なら数値データをその配置先へコピーします。** すでに同じdevice・dtypeなら、`to()`は元のTensor自身を返す場合があります。このCPU例ではGPUへの転送は起きません。[Tensor.toの仕様](https://docs.pytorch.org/docs/2.14/generated/torch.Tensor.to.html)

辞書内包表記の`key: ...`は「1組をどう作るか」、`for ... in ...`は「材料をどこから順に取るか」です。普通のfor文とは文法が異なるため、for部分の末尾に`:`を付けません。[Pythonの辞書内包表記](../python-objects/)に、値・キーの変換と新規作成の小さな例があります。

`BatchEncoding`には各Tensorをまとめて移す`.to(device)`もあります。Tokenizerから受け取った直後なら`encoded_inputs.to(device)`を使えますが、通常のdictへ変えた`inputs`にはこのメソッドはありません。この例はモデル全体をCPUに置いています。複数デバイスへ分散した場合の配置は、[実行環境](../../environment/)の条件も確認します。

### withとno_gradは何を変えるか

`with`は、処理の範囲に入るときと抜けるときの管理を行うPython構文です。`with torch.no_grad():`では、字下げした範囲の計算について、逆伝播のための演算記録を止めます。抜けると元の勾配記録の設定へ戻ります。

計算やHidden Stateの取得は実行されます。重みの`requires_grad`を永久に無効化する操作ではなく、`model.eval()`のモード切替とも別です。損失（loss）は予測を評価する値、勾配はその損失が重みなどの変化にどう反応するかを表します。[Autogradと勾配](../autograd/)で小さな式から確認できます。

### tuple全体と、取り出した1個のTensor

`hidden_states`は順序付きの容器であるtuple、`hidden_states[0]`はそこから取り出した1個のTensorです。tupleの要素を別のものへ入れ替えることはできませんが、中のTensorの数値まで変更不能になるわけではありません。ここでは観察だけを行い、数値を書き換えません。

```python
for i, state in enumerate(hidden_states):
    print(i, list(state.shape))
```

`enumerate`は「番号と要素」を組で渡します。最初の周回では`i=0`、`state=hidden_states[0]`、次は`i=1`、`state=hidden_states[1]`です。ここでは全29個のshapeを確認できます。

### 28層なのに、なぜ29個あるか

**tupleの番号はDecoder Layer番号ではありません。** Embedding後の状態が最初に入り、その後の状態が続きます。以下の各保存地点のshapeはすべて`[1, 7, 1024]`です。

| 式 | 参照するもの |
|---|---|
| `model.model.layers[0]` | 計算を行うQwen3DecoderLayerの実物 |
| `hidden_states[0]` | その層へ入る前のTensor |
| `hidden_states[1]` | その層を通った後のTensor |

Layer 0は実在しますが、処理する部品と、その部品が扱うデータは別です。Embeddingの出力とLayer 0へ入るTensorの値は一致しても、Layer 0という部品そのものがそのTensorなのではありません。

```text
整数ID [1, 7]
  ↓ Embedding
hidden_states[0]  ← Layer 0に入る前
  ↓ Layer 0
hidden_states[1]  ← Layer 0後・Layer 1に入る前
  ↓ Layer 1
hidden_states[2]
  ↓ … Layer 2〜26 …
hidden_states[27] ← Layer 26後・Layer 27に入る前
  ↓ Layer 27（最後の層）
  ↓ 最終RMSNorm
hidden_states[28] ← 最終RMSNorm後
  ↓ LM head
logits [1, 7, 151936]
```

| 保存された状態 | 観察している場所 |
|---|---|
| `hidden_states[0]` | 入力Embeddingの出力 |
| `hidden_states[1]`〜`[27]` | Layer 0〜26の出力 |
| `hidden_states[28]`（`[-1]`） | Layer 27を通り、さらに最終RMSNormを通った出力 |

最後の状態を「Layer 27直後」とだけ呼ぶと、最終RMSNormの処理を見落とします。今回の実装では、Layer 27の生の出力はこのtupleに別の項目として入りません。この対応はTransformers 5.18.0のQwen3実装と、各層・最終Normの出力を実際に照合して確認しています。[Qwen3の実装](https://github.com/huggingface/transformers/blob/v5.18.0/src/transformers/models/qwen3/modeling_qwen3.py)

### 「こんにちは」の位置の先頭8成分を追う

```python
before_layer0 = hidden_states[0]
after_layer0 = hidden_states[1]
print("Layer 0前:", before_layer0[0, 0, :8])
print("Layer 0後:", after_layer0[0, 0, :8])
print("Tensor全体が近い値か:", torch.allclose(before_layer0, after_layer0))
```

```text
Layer 0前: tensor([ 0.0140, -0.0510,  0.0308,  0.0250,  0.0118, -0.0352,  0.0242,  0.0557],
       dtype=torch.bfloat16)
Layer 0後: tensor([-0.2207,  0.4219,  0.1211, -0.6328,  0.0732,  0.2676, -0.6094,  0.5078],
       dtype=torch.bfloat16)
Tensor全体が近い値か: False
```

| `hidden_states[i][0, 0, :8]`の指定 | 選んでいるもの |
|---|---|
| `i` | 保存された状態の番号 |
| 最初の`0` | 入力1件のうち0番目 |
| 次の`0` | 入力内のトークン位置0（今回のIDは89015） |
| `:8` | 1024成分のうち成分0〜7 |

カンマを一つ減らした`before_layer0[0, 0:8]`は、トークン位置を切り出します。今回の7トークンならshapeは`[7, 1024]`で、先頭トークンの8成分ではありません。`before_layer0[0, 0, :8]`ならshapeは`[8]`です。

`hidden_states[0][0, 0]`は`weight[89015]`を引いたベクトルと一致します。Layerを通った後は、**「ID 89015の重み表の行」ではなく、「こんにちは」がある位置の内部表現**を見ています。shapeと位置の対応は保たれますが、ベクトルの値は更新されます。元のEmbeddingの行を学習で更新した結果ではありません。

Qwen3は未来を見ない因果的なAttentionを使います。この文の位置0には前のトークンもないので、後ろの「今日はいい天気ですね」を参照して値が変わったわけではありません。文脈による変化を観察したい場合は、前のトークンを参照できる後ろの位置も比較します。会話テンプレートを加えると、位置0が「こんにちは」とは限らなくなります。

### allcloseのFalseから分かること

表示したのは先頭8成分ですが、`torch.allclose(before_layer0, after_layer0)`は**1×7×1024＝7168個の対応する全成分**を比較します。すべてが許容誤差内なら`True`、一つでも範囲を外れれば`False`です。「すべての成分が変わった」「意味が良くなった」とまでは分かりません。

先頭8成分だけを比べるなら、両引数を`[0, 0, :8]`で切り出します。`a == b`は要素ごとの完全一致を表すbool Tensor、`torch.equal(a, b)`は同じshape・値かを一つのboolで返します。`allclose`は許容誤差付きの比較です。

既定の許容誤差は`rtol=1e-5`、`atol=1e-8`です。bfloat16を渡しても、自動的に粗い精度へ合わせて緩くなるわけではありません。演算環境をまたいで数値を比較するときは、目的に合う誤差を指定します。[allcloseの仕様](https://docs.pytorch.org/docs/2.14/generated/torch.allclose.html)

<details>
<summary>同じ位置を全29状態で追うコード</summary>

```python
for i, state in enumerate(hidden_states):
    if i == 0:
        label = "Embedding後・Layer 0前"
    elif i == len(hidden_states) - 1:
        label = "最後のLayer後・最終RMSNorm後"
    else:
        label = f"Layer {i - 1}後・Layer {i}前"
    print(f"hidden_states[{i}] — {label}", state.shape)
    print(state[0, 0, :8])
```

各行の8成分はベクトルの一部です。例えば先頭成分が同じでも残り1016成分まで同じとは限らず、bfloat16の丸めで小さな変化が表示へ出ない場合もあります。大きい値だけから計算の故障や意味を断定せず、Layer内の計算や正規化を別に観察します。

</details>

<details>
<summary>比較時にIndexErrorが出たら、変数の型を確認する</summary>

次のように受け取り側へ同じ名前を使うと、`hidden_states`がtuple全体から1個のTensorへの参照に変わってしまいます。これは問題を説明する例で、観察コードへ追加するものではありません。

```text
for i, hidden_states in enumerate(hidden_states):
    print(i, hidden_states.shape)
```

通常のfor文の受け取り変数は、ループ終了後も残ります。最後には`hidden_states`が`[1,7,1024]`のTensorになるため、`hidden_states[1]`は「状態の1番目」ではなく「batch軸の1番目」を取ろうとして範囲外になります。

受け取り側を`state`や`hidden_state`に分け、必要なら`hidden_states = outputs.hidden_states`でtupleへの参照を戻します。比較直前に`type(hidden_states)`と`len(hidden_states)`を確認し、今回ならtuple・29個であることを確かめます。単数形・複数形のつづりに特別な文法規則があるのではなく、異なる変数名にすることが重要です。

</details>
