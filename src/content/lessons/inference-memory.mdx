## メモリを三つに分ける

| 対象 | 何に依存するか |
|---|---|
| 重み | パラメータ数、保存dtype、共有、量子化形式 |
| 活性値・一時領域 | batch、系列長、hidden size、計算方式 |
| KV Cache | 層数、batch、系列長、KV head数、dtype |

学習ではさらに勾配やoptimizer state、保存する活性値が必要になります。

## 論理的な容量を計算する

```python
import torch
x = torch.zeros(2, 7, 1024, dtype=torch.float32)
print(x.numel())
print(x.element_size())
print(x.numel() * x.element_size())
```

```text
14336
4
57344
```

これは数値データの論理容量です。Tensorがviewでデータを共有する場合、複数のTensorの値を足しても実メモリ量とは一致しません。

## GPUの計算は非同期

Pythonが演算を呼び出してから戻る時間だけでは、GPUの処理完了時間を測れない場合があります。測定前後で同期し、warmup後に複数回測ります。

```python
import time
torch.cuda.synchronize()
start = time.perf_counter()
with torch.inference_mode():
    result = model.generate(**inputs, max_new_tokens=32, do_sample=False)
torch.cuda.synchronize()
elapsed = time.perf_counter() - start
print(elapsed)
```

CUDA上のモデルと入力があることが前提です。具体的な秒数は環境依存なので固定値を示しません。

## Cacheの有無を同じ生成条件で測る

[KV Cache教材](../kv-cache/)の`model`と`generate_tokens`を用意した後に実行する例です。モデルの読み込みは測定に含めず、両方式とも同じ個数を生成します。各呼び出しは空のcacheから始まります。

```python
import time

def benchmark(generate_fn, num_runs=3):
    if num_runs < 1:
        raise ValueError("num_runsは1以上にします")
    times = []
    model_device = next(model.parameters()).device

    def synchronize():
        if model_device.type == "cuda":
            torch.cuda.synchronize(model_device)

    generate_fn()  # warmup：初回の準備を測定から外す
    for _ in range(num_runs):
        synchronize()
        start = time.perf_counter()
        result = generate_fn()
        synchronize()
        times.append((time.perf_counter() - start) * 1000)
    return sum(times) / len(times), result

num_new_tokens = 32
plain_ms, (plain_ids, _) = benchmark(
    lambda: generate_tokens(False, num_new_tokens),
)
cache_ms, (cached_ids, _) = benchmark(
    lambda: generate_tokens(True, num_new_tokens),
)
print("なし / あり (ms):", plain_ms, cache_ms)
print("速度比:", plain_ms / cache_ms)
print("生成ID列が一致:", torch.equal(plain_ids, cached_ids))
```

`generate_fn`には**関数そのもの**を渡し、`generate_fn()`で実行します。`lambda`は引数を指定した呼び出しを、後で実行できる関数に包んでいます。`times`に各回の時間を入れ、平均を返します。表示・文字列への変換・ID比較は測定区間の外です。CPUでも使え、GPUでは処理完了を待ってから終了時刻を取る、実際の待ち時間の測定です。

### 戻り値を分けて受け取る

上の`generate_tokens`は`(ID列, cache)`を返します。`benchmark`はさらに平均時間を組み合わせるので、返り値は`(平均ms, (ID列, cache))`です。`plain_ms, (plain_ids, _) = ...`は、その入れ子を対応する名前へ分けて受け取る**アンパッキング**です。`result`は毎回上書きされ、返されるID列は最後の測定回のものです。

`for _ in range(num_runs)`や戻り値の`_`は、「この値は使わない」という慣例です。`_`自体も普通の変数名で、特別な破棄命令ではありません。

### CUDA Eventで測る場合の読み方

CUDA Eventは、GPUのstream上に置いた2つの目印の間の経過時間を測ります。上の同期つき時計とは測定方法が異なるため、どちらを使ったか記録します。[PyTorchのEvent仕様](https://docs.pytorch.org/docs/2.14/generated/torch.cuda.Event.html)

| 処理 | 意味 |
|---|---|
| `torch.cuda.synchronize()` | 前のGPU処理を終える |
| `torch.cuda.Event(enable_timing=True)` | 時間を測れる目印を作る |
| `start.record()` → 生成 → `end.record()` | 同じstreamへ開始・終了の目印を置く |
| `end.synchronize()` | 終了の目印へ到達するまで待つ |
| `start.elapsed_time(end)` | 2つの目印の間の経過時間をmsで取得 |

これは演算カーネルの実行時間だけを足した値とは限りません。目印の間でGPUがCPUからの次の指示を待つと、その待ち時間も含まれ得ます。短い生成の測定値だけから、行列演算やメモリアクセスのどれが主な原因かを断定しません。

### 計算量の減少と、速度比は同じではない

cacheは過去位置の射影やMLPの再計算を省きますが、新しいQと過去Kの比較、Vの加重和、cacheの読み書きは残ります。短い生成ではPythonの呼び出しやGPUへの処理発行などの負担も効くため、**cacheありなら必ず何倍になる、とは決まりません**。

入力P個からN個を選び、最後に選んだIDのForwardは省くループで、今回入力するToken位置を延べ数で比べます。

| 生成数N（入力P=7） | cacheなし | cacheあり |
|---|---|---|
| 32 | `7 + 8 + … + 38 = 720` | `7 + 31 = 38` |
| 1024 | `7 + 8 + … + 1030 = 530,944` | `7 + 1023 = 1,030` |

一般にはcacheなしが`N × P + N × (N − 1) / 2`、cacheありが`P + N − 1`です。これはEmbeddingやMLPへ入力する位置数の比較で、Attentionの参照量や総演算回数そのものではありません。両方式ともForwardはN回呼び、GPUは複数位置をまとめて処理できるため、この比率をそのまま速度比にはできません。

出力する速度比は`なしの時間 ÷ ありの時間`です。2ならcacheありの時間は半分、1なら同じ、0.5ならcacheありの時間は2倍です。

まず同じ短い生成でID列と長さを確認し、その後に入力長・生成長を変えて比較します。大きく伸ばすと時間とメモリも増えます。Greedyでも演算精度などによって結果が分かれる場合があるので、一致しない結果を隠さず記録します。

実験コードの`NUM_NEW_TOKENS`や`NUM_RUNS`も普通のPython変数です。大文字は「設定値として扱う」という慣習で、自動的に変更不可になるわけではありません。

ファイルのトップレベルで定義した設定値は、関数内から読み取れます。上のコードでは、測定回数は`num_runs`という引数で受け取り、生成数は`lambda`から渡しています。関数の外にある値を読むことと、その名前へ関数内で代入することは別です。[Pythonの関数と名前の参照](https://docs.python.org/3/tutorial/controlflow.html#defining-functions)

## 指標をそろえる

TTFTは最初の出力まで、tokens/sはある範囲の生成速度です。入力長、実際の生成長、batch、cache有無、dtypeをそろえます。モデル読み込みやダウンロードの時間を含めるかも明示します。

## 量子化へつなぐ

重みを小さくしても、cacheや一時領域が支配的なら全体の削減率は同じになりません。低bit計算に対応するカーネルがなければ、復元処理などで速度が改善しない場合もあります。
