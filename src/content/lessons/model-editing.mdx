## 変更する前に、境界を見る

module名、入力と出力のshape、dtype、deviceを調べます。モデル全体を一度に書き換えるより、一つのLinearやMLPなどの境界を選ぶと比較しやすくなります。

## Hookでshapeを観察する

```python
import torch
from torch import nn

layer = nn.Linear(3, 2)
def observe(module, inputs, output):
    print(inputs[0].shape, output.shape)

handle = layer.register_forward_hook(observe)
_ = layer(torch.ones(1, 3))
handle.remove()
```

```text
torch.Size([1, 3]) torch.Size([1, 2])
```

観察が終わったらhandleを外します。巨大な活性値をそのまま保存するとメモリを圧迫するため、shapeや小さな集計から始めます。

## Freezeは学習対象を変える

```python
for parameter in layer.parameters():
    parameter.requires_grad_(False)
print(sum(p.numel() for p in layer.parameters() if p.requires_grad))
```

```text
0
```

これは勾配計算対象を外す操作です。推論でその層の計算がなくなるわけではありません。optimizerへ渡したパラメータとの整合も確認します。

## 小さな置換を試す

同じ入力・出力shapeを持つ層を、別実装に置き換えるところから始めます。Residualへ戻るshapeが合っていても、数値のスケールや役割が違えば品質は変わります。Identityへの置換は、層を無効化するablationとして役立ちますが、改善を保証しません。

## 活性化関数を交換して生成を比べる

Qwen3-0.6BのLayer 27で、MLPの `act_fn` をSiLUからReLUへ交換します。MLPは、入力をgateとupへ射影し、gate側に活性化関数を適用してから両者を要素ごとに掛け、downで元の幅へ戻します。

```text
入力 [B,T,1024]
  ├─ gate_proj → act_fn ─┐
  └─ up_proj ───────────× → down_proj → [B,T,1024]
                 [B,T,3072]
```

SiLUは各値にそのSigmoidを掛け、ReLUは負の値を0、正の値をそのまま返します。例えば入力が-1なら、SiLUは約-0.2689、ReLUは0です。その後up側と掛ける値が変わり、出力まで影響します。RMSNormは同じ位置の成分全体から尺度を計算しますが、これらの活性化関数は各成分に非線形変換を適用します。

`mlp = model.model.layers[27].mlp` はモデル内部のインスタンスへの参照です。その属性にReLUのインスタンスを代入すると、その層を通るすべてのToken位置でReLUが使われます。Prefillの全文と、その後のDecodeで処理するTokenの両方が対象です。[Head Ablation](../attention-sink/)で末尾位置の特定Headだけを止めた実験から、介入範囲が変わります。

### 同じチャット入力で比較する

[モデルとTokenizerを読み込む](../../recipes/load/)の準備後、次を実行します。添付の実験と同じ質問・Layer・生成上限を使い、1ビームの貪欲生成を明示します。

```python
messages = [{"role": "user", "content": "雨が降る仕組みを簡単に説明してください。"}]
prompt = tokenizer.apply_chat_template(
    messages, tokenize=False, add_generation_prompt=True, enable_thinking=False,
)
inputs = tokenizer(prompt, add_special_tokens=False, return_tensors="pt").to(model.device)
model.eval()

def generate_ids():
    with torch.inference_mode():
        ids = model.generate(**inputs, max_new_tokens=500, do_sample=False, num_beams=1)
    return ids[0, inputs["input_ids"].shape[1]:]

original_ids = generate_ids()
mlp = model.model.layers[27].mlp
original_activation = mlp.act_fn
try:
    mlp.act_fn = torch.nn.ReLU()
    modified_ids = generate_ids()
finally:
    mlp.act_fn = original_activation

print(tokenizer.decode(original_ids, skip_special_tokens=True))
print(tokenizer.decode(modified_ids, skip_special_tokens=True))
assert mlp.act_fn is original_activation
```

同じ関数を2回呼び、その時点のモデルで生成します。各生成は同じ入力から新しく始まり、前の生成のCacheを渡しません。`finally` は途中で生成が失敗した場合にも、保持した元のModuleを再登録します。Notebookで次の実験を行うときも、復元後の状態から始められます。SiLUとReLUは学習可能な重みを持たないため、この交換ではoptimizerによる更新を行いません。

<summary>入力・生成結果・終了Tokenを区別する</summary>

今回の `enable_thinking=False` では、空のthinkブロックを閉じるところまでが入力に含まれます。Tokenizerが返すのは質問と応答開始部分のIDで、回答はその後の `generate()` が末尾に追加します。`add_special_tokens=False` はテンプレートにある特殊Tokenを保ち、さらに自動付加する処理を止める指定です。

`generate()` の返り値には入力と生成部分が含まれます。`inputs["input_ids"].shape[1]` で入力の幅を求め、その後ろだけを切り出します。生成部分を関数内でも呼び出し元でもprintすると、同じ回答が2回表示されます。

`max_new_tokens=500` は新しく生成するToken数の上限です。設定されたEOSを選べば上限より前に終了します。終わり方を調べるときは、特殊Tokenを含めて末尾を表示します。

```python
print("生成Token数:", len(modified_ids))
print("末尾:", repr(tokenizer.decode(modified_ids[-1:], skip_special_tokens=False)))
print("終了IDの設定:", model.generation_config.eos_token_id)
```

上限に達したかだけで終了原因を決めず、末尾IDとEOS設定も確認します。1回のForwardを行う `model()` に対し、Transformersの `generate()` はForwardとToken選択を繰り返します。その内部のTensor計算はPyTorchが担います。

</details>

<details>
<summary>提供元と実行の仕組みをコードから読む</summary>

| コード | 担当するもの |
|---|---|
| tokenizer.apply_chat_template / tokenizer.decode | TransformersのTokenizerが、会話書式・文字列・IDを変換 |
| model.generate | TransformersがForward、Token選択、Cache、終了条件を管理 |
| model.eval / torch.inference_mode | PyTorchが層の動作モードと勾配記録を制御 |
| mlp.act_fn | Qwen3MLPがForward中に呼び出す活性化Module |

SiLU自体は汎用的な活性化関数で、PyTorchにも `torch.nn.SiLU()` があります。Qwen3のMLPはその計算をgate側で使う構造です。

`do_sample=False` は生成設定、`torch.argmax()` は最大値の位置を返す演算です。1ビームの貪欲生成では最大の候補を選びますが、生成設定によるスコア調整が入ると、生のlogitsへ直接argmaxした結果とは異なる場合があります。

`finally` 内でも通常のPythonと同じく、例外が起きた行で処理が中断します。復元の代入が成功した後に表示処理が失敗した場合、復元自体は完了しています。

</details>

### 文章の変化をどう評価するか

提供された実行結果では、通常の「以下のプロセスがあります」が、交換後は「以下のプロセスが考えられます」に変わっていました。最初に異なるTokenを選ぶと、それ以降は過去の生成Tokenも異なるため、文章全体の違いへ広がります。

両方の回答に、体の乾燥を雨の原因とする不正確な説明が含まれていました。この比較で確認できるのは生成への影響で、性能の評価には[未使用データでの評価](../evaluation/)が必要です。固定した同じ入力に対するlogits比較と、自己回帰生成で変わっていく文章の比較を併用します。[短い活性化関数の差し替えコード](../../recipes/swap/)も利用できます。

交換はメモリ上のモデルに対して有効です。SiLUとReLUの違いは重みTensorに記録されないため、state_dictだけではこの変更を再現できません。特定のLayerだけ変更した構造を保存・再利用する場合、読み込み後の同じ差し替え手順も必要です。

## Head・Norm・RoPEも変更対象になる

重みの数値だけでなく、それを使う計算構造も研究対象です。Qwen3-0.6Bでは次の違いを分けて考えます。

| 変更するもの | 影響する箇所 | 比較する条件 |
|---|---|---|
| Q Head数・head_dim | 独立したAttention計算と1 Headの幅 | 射影の出力幅、RoPE、o_projとの整合 |
| KV Head数・対応順 | K/Vの共有とcache容量 | 同じToken数・層数・dtypeで品質と容量を比較 |
| RMSNormの位置・方式・eps | 特徴のスケール、勾配、Attentionスコア | 元モデルと同じ入力・評価条件 |
| RoPEの速度・基準値 | 位置差が内積へ与える効果 | 短文と長文の両方の品質 |

Headを増やすほど良いとは限りません。`16×128`と`32×64`は合計2048成分でも、Attentionの計算単位が変わります。reshapeやconfigだけの変更では、重み・Norm・位置処理を含む整合性まで保証できません。

学習済みモデルのNormを外すなどの**ablation**は「その重みが元の部品にどれだけ依存するか」を調べる実験です。別構造を最初から学習して比較する実験とは分けます。ablationで品質が落ちても、その構造が一般的に劣るとは断定できません。

## state_dictと構造

state_dictは重みやbufferの対応を持ちますが、Pythonのモデル実装そのものではありません。構造を変えたら、読み込み側も対応する必要があります。missing/unexpected keysを無視して成功としないようにします。

## 元へ戻れる単位で実験する

元の重み・configを保持し、変更箇所・仮説・評価結果を記録します。モデル改造はコード変更だけでなく、前後の比較と復元を含む作業です。
