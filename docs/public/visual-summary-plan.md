# LLMを図でつなぐまとめページ：調査と実装計画

作成日：2026-10-06。状態：実装済み。以下は設計時の計画と判断。まとめ6ページと小モデルの実行教材を追加し、操作・リンク・小画面・学習例を検証した。

## 2026-10-06のUI見直し

全体地図を準備・推論・学習・改造が同じ面にある表示へ変更した。詳細ページと小モデル教材は、各地点の入力・処理・出力・短い変換理由を常時表示する。長いコードと条件はnative dialogの補足へ分け、初期表示から全体を追うための地点切替は不要にした。幅に応じた折返しと番号・矢印で順序を示し、並列の変更候補には順序の矢印を付けない。値の枠に内側の余白を設け、地図用の短い表記と完全な実測記録を分けた。

検証：まとめと小モデル教材の初期表示、768・390・320px、明暗テーマ、補足のEnter・Escape・フォーカス復帰、直リンク復元、JavaScript無効時の主表示。検証用画像はローカルへ保存し、公開ビルドへ含めない。

## 目的

学んだ用語とコードを、LLMの中での場所・処理・データの変化・変更の影響へ結びつける。読者が図の一地点から「何が入るか」「誰が何をするか」「何が出るか」「どこを変えられるか」を説明できることを目標とする。

## 推奨構成：入口1ページ＋詳細5ページ

配置は `/learn/maps/` を推奨する。「学ぶ」内に「図でつなぐ」を設け、ホームと学習マップにも入口を置く。新しい主要タブを増やすより、学ぶための別の入口としてまとめる。表示中の上部ナビ・左ナビ・パンくずを同じ所属にそろえる。

### 1. 全体を見渡す — `/learn/maps/`

最初に「使う・作る／学習する・改造する」を並列の道筋として表示する。モデルの実物へ、構造を作るコード・設定・重み・Tokenizerがどう関係するかを小さな準備図で示す。

- 使う：入力 → 数値変換 → モデル計算 → 次のIDを選ぶ → 文章表示。
- 作る／学習する：データと構造を用意 → 初期化 → 損失・勾配・更新 → 評価 → 保存。
- 改造する：基準を記録 → 対象を選ぶ → 変更 → 比較 → 保存・再読込／復元。
- 入口の図は8個程度までのまとまりに絞り、詳しい内部は詳細ページへ進む。
- 既存の用語を選ぶと図中の位置が強調され、関連教材・実験へのリンクが出る。

推論の後に必ず学習するような一本の矢印は作らない。用途の分岐、処理順、重みの依存、更新の反復を別の関係として表す。

### 2. 文章が回答になるまで — `/learn/maps/inference/`

画面の中心を「入るデータ → 処理する部品とコード → 出るデータ」の連続図にする。上部の小さな全体図に現在地点を表示し、下で一段ずつ追う。

初期例は既存の「こんにちは、今日はいい天気ですね」。会話テンプレートを適用しない生文の例として、既存実測の7トークンを使う。会話形式は別モードで境界トークンを示し、トークン数を再計算する。

| 段階 | コードとの対応 | 図で見せるデータ |
| --- | --- | --- |
| 文章をIDへ | `tokenizer.encode(..., return_tensors="pt")` | 文章 → 7個の整数ID、`[1,7]` |
| 各IDの行を引く | `embedding = model.get_input_embeddings()`、`embedding(ids)` | 重み表から7本を取得、`[1,7,1024]` |
| 文脈を反映する | モデル内部のDecoder Layer | shapeを保ち、各位置のベクトルの値が変わる |
| 候補のスコアを作る | `lm_head`、`outputs.logits` | 基本形は`[1,7,151936]`、数値は未実測なら模式表示 |
| 次のIDを選ぶ | 最後の位置、greedy／sampling | `[1,151936]`の候補から次のIDを選ぶ |
| 列に追加して繰り返す | `model.generate(...)`の内部の役割 | 生成列の長さが7→8→…、停止とCache |
| 表示する | 新規部分をsliceして`tokenizer.decode(...)` | ID列 → 文字列 |

`get_input_embeddings()`は層を取得する操作、`embedding(ids)`はデータを変換する呼び出しとして分ける。手動の内部観察コードと`generate`の実行を、同じプログラムの連続行として混在させない。

最初は最後の位置の最大スコアを選ぶgreedyを示し、samplingで確率を使う場合を後から重ねる。毎回必ずsoftmaxを実行する図にはしない。生成列全体と、Cache使用時にモデルへ渡す新規ID・位置情報の違いも補助図で説明する。

### 3. モデルの中を拡大する — `/learn/maps/structure/`

モデル全体 → 28個のDecoder Layer → 1層 → Attention／MLPへ拡大する構成。初期表示は全体図、部品を選ぶと入出力と短い計算説明が開く。

- 全体：Embedding → Decoder Layer ×28 → final RMSNorm → LM head。
- 1層：入力 → RMSNorm → Attention → Residual加算 → RMSNorm → MLP → Residual加算。
- Attention：Q/K/V投影、Q/KのNorm・RoPE、causal mask、情報の加重和、出力投影。初期図を細かくしすぎず、必要時に展開する。
- MLP：gate/up → 活性化と要素積 → down。
- 左に部品の所有関係、中心にデータの通る順序、詳細にmodule名・重みshape・入力／出力shapeを置く。
- Qwen3-0.6BのQ=16 heads、KV=8 heads、head_dim=128を固定configから表示する。
- 重み表と通過する活性値を区別し、shapeが同じでも数値や役割が変わる場所を示す。
- 入力EmbeddingとLM headの重み共有を、処理の矢印とは違う線と文字ラベルで示す。

既存のModel Inspectorと同じconfigを使う。構造に基づく図と、hookで実測した表示を区別する。

### 4. LLMを作り、学習させる — `/learn/maps/training/`

上段に作成の工程、下段に学習一回の拡大図を置く。

作成の工程：目的とデータ → 分割 → Tokenizerの用意 → 構造と設定 → 重みの初期化 → 学習 → 未使用データで評価 → 保存・再読込 → 推論。

学習一回：batchのIDとlabels → forward → logitsと正解の対応 → loss → `backward()`で勾配 → `optimizer.step()`で対象重みを更新 → 次のbatch。`zero_grad()`は勾配をクリアする位置に表示する。

- 「新規初期化」「学習済みモデルを追加学習」「LoRA」の開始状態・更新範囲を比較する。
- 同じ入力列の隣接位置で「ここまでの入力から、次のトークンを予測する」を図示する。labelsの内部shiftを使うAPIと手動shiftを分ける。
- attention maskとlossへ寄与する位置のマスクを、役割で区別する。
- 重み・活性値・loss・勾配を別々のデータとして表示する。
- `model.train()`、勾配記録、勾配計算、重み更新の役割を図中で対応させる。
- 一から作る実行例はCPUでも扱える教育用の小モデルを別教材で用意する。Qwenの学習済みベクトルを、その小モデルの初期値・学習結果として流用しない。
- Tokenizerを既存のものから用意する選択と、新しく学習する選択を示す。全読者に新規Tokenizer学習を必須としない。

ここでは大規模モデルの商用品質の完成を約束せず、「作成の各工程と成果物を理解し、小例で更新を追える」を到達点にする。

### 5. どこを改造すると、何が変わるか — `/learn/maps/modification/`

既存のモデル図に変更箇所を重ね、対象を選ぶと「変更前／変更後」「影響先」「確認すべきこと」「既存の改造課題」を表示する。

| 対象 | 図で見せる変化 | 確認すること |
| --- | --- | --- |
| 生成設定 | 最後の候補選択の条件 | 同じlogitsでも選ばれるIDが変わり得る |
| Embeddingの行 | 特定IDのベクトルと、共有LM headへの影響 | 共有の有無、対象IDを含む／含まない入力、復元 |
| 語彙追加 | Tokenizerの追加IDとEmbedding／出力層の新しい行 | 行数とIDの整合、重み共有、追加行の学習 |
| LoRA | 元のLinearに小さな更新経路を加える | 更新する対象、基盤モデル、adapterの保存 |
| 量子化 | 保存表現・計算方式・復元近似 | 誤差、品質、実測メモリ・速度 |
| 層の置換 | 処理経路の一部を変更する | shapeと戻り値形式、実行、品質、復元 |

すべてを「重みを書き換える改造」と一括にしない。比較の共通工程は「基準 → 一つの変更 → 同条件で評価 → 再読込／復元」。改善しなかった結果も扱う。RAGやTool Useなど外側の組み合わせは、周辺技術への関連リンクで示す。

### 6. プログラム・ファイル・実行環境をつなぐ — `/learn/maps/runtime/`

「読み込む前」「メモリ上で使う」「保存して読み直す」の3領域を図にする。

- モデルID／revision → ファイルの取得・選択。
- Tokenizerの語彙・設定・テンプレート → Tokenizerインスタンス。
- モデルの実装コード＋config＋重みファイル → modelインスタンス。
- Pythonの変数と、その参照先のオブジェクト・属性・呼び出し・返り値。
- Transformersがモデルと生成処理を組み立て、PyTorchがTensor演算を扱い、選んだdeviceで実行する関係。
- `.to(device)`、dtype変換、shape変換、Embeddingの参照を別の変化として示す。
- `save_pretrained()` → 重み・config・Tokenizerの保存 → 別プロセスで再読込。
- LoRA adapterと基盤モデルの関係、独自の構造では実装コードも必要になること。

最初は単一CPUまたは単一GPUの基本形を表示し、分散配置・推論エンジン・変換形式は詳細を展開する。CUDAの実行をブラウザーのアニメーションで実測したように表示しない。

## 全ページに共通する見せ方

1. 最初に主役の図と一文の目的を見せる。長い本文を読む前に流れをつかめる。
2. データは「値・型・shape・軸の意味」、処理は「部品名・コード・変化の理由」をそろえる。
3. ノードの選択で、その処理の入力・出力を同時に強調する。段階を進めても例文と変数を維持する。
4. 詳細欄は「入る → 処理する → 出る → 確認するコード → 関連教材・実験・API」。主要説明はクリックしなくても読める。
5. 実測、説明用固定値、仕様例、模式図を各表示の近くで区別する。未計測は未計測と示す。
6. shape変化だけでなく、値・意味・所有者・配置先・保存状態の変化も示す。
7. 処理順、包含、共有、更新、反復には文字ラベルを添える。線の色だけで意味を伝えない。
8. スマートフォンでは縦方向へ再配置し、固定の巨大画像の縮小やパン・ズーム操作を前提にしない。
9. 図の選択はキーボードにも対応し、テキストの手順一覧を同じ情報から生成する。自動再生はせず、動きを減らす設定を尊重する。
10. 読了管理より、現在のページ・図の選択地点を示す。初期表示で全分岐・全数値を展開しない。

## 実装計画

### 第1段階：最も必要なつながりを作る

全体・推論・作成と学習の3ページを制作する。推論のEmbedding地点を既存の実測に対応させ、学習側は小例でloss・勾配・更新を追う。初期HTMLだけでも図の意味と関連リンクが読めるようにする。

### 第2段階：モデルの拡大と改造を接続する

構造・改造の2ページを制作する。部品の包含と実行順を分け、共有重みや語彙拡張など複数箇所に影響する変更を図で確認する。

### 第3段階：実際のプログラムと成果物へ接続する

プログラムとファイルのページ、小モデルの作成・学習教材を制作する。前の段階でもファイルの基本説明は残す。ここで詳細を補い、新規初期化・学習・保存・再読込の通し例を検証する。

実装候補：`src/data/maps.ts`にノード・関係・表示条件・教材リンクを持たせ、`src/pages/learn/maps/`で静的ページを生成する。共通の図は意味のあるHTMLを主体にし、関係線が必要な箇所へSVGを使う。選択と段階表示だけReactの部品として追加する。画像生成や外部サービスの埋め込みを必須にしない。

`SiteLayout.astro`の学ぶ内ナビ、ホーム、学習マップ、構造化検索索引・Pagefind、内部リンク検査へ追加する。Pagesのbaseを既存の`withBase()`で扱う。モデル本体のブラウザー実行は、このまとめの成立に必要な条件にしない。

## 完了の確認条件

- 任意の段階から、入力・処理・出力と、そのコードに対応する部分が分かる。
- 実測例の値・shape・モデルrevisionが参照fixtureと一致する。
- 図の一段だけを見ても、ID・位置・ベクトル成分を混同しない。
- 同じshapeのまま値が変わる処理、重みが更新される処理を説明できる。
- 推論・新規作成・追加学習・直接改造の開始状態と結果が区別できる。
- 学習のshift・mask・更新対象、QwenのQ/KVのhead数、重み共有が正しい。
- 図、説明、コード、教材・実験・APIリンクに矛盾がない。
- 選択・戻る・直リンク・現在地点・スマートフォン・拡大・明暗テーマ・キーボードを確認する。
- 型検査、必要な計算検証、リンク・公開境界検査、Pagesのサブパス検証が通る。

実装時の検証：型検査、単体19件、Pages用操作9件、185ページの内部リンク検査が成功。320px幅で長いrevision文字列が作る横はみ出しを修正した。小モデルはCPU・float32で120回更新し、学習用／未使用文のloss、勾配、重み変化、causal mask、別プロセス再読込を検証した。実スクリーンリーダーでの通読や実機の全機種検証は未実施。
