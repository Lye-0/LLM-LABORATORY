# Notion学習ページのまとめ方

更新：2026-10-04 ／ 第2版

> **会話や実験をそのまま保存するのではなく、後から読んで仕組みを理解し直せる説明ページにする。**
> 前から読めば理解が進み、必要なときには「どの対象の、どの処理・性質か」を見つけられる構成にする。

このガイドは、Tokenizerのページ作成・修正を通じて決めた方針を、今後の学習単位にも使える形に整理したものです。主にNotionの「仕組み」内で使い、LLM関連は「◆ LLM」セクションの下に整理します。実験フォルダの単位は参考にしますが、実験記録や操作手順書を作るための規則ではありません。

**第2版では、別の処理の結果は分け、同じ変数・オブジェクトの確認結果はまとめる、という区別を本文・ひな型・チェックリストへ統合しています。** 初版の「まとめて出力を掲載しない」は、複数の異なる処理を一括表示しないという意味であり、同じ対象の複数の性質まで切り離す指示ではありません。

**まず押さえる原則**

| 原則 | 判断基準 |
|---|---|
| 説明ページにする | 時系列や操作手順より、役割・仕組み・使い方を中心にする。 |
| 前提を先に置く | インポート、対象の指定、オブジェクトの準備を、その利用より前に説明する。 |
| 別の処理は分ける | `tokenize()`・`encode()`・`decode()`など、別の変換はそれぞれ「コード → 対応する結果 → 読み取り」にする。 |
| 同じ対象はまとめる | 一つの変数の値・型・形状・デバイスなどと、その結果の解説は同じ節に集める。 |
| 確認する式を見せる | 「型」だけでなく`type(tokenizer)`、「形状」だけでなく`tensor.shape`を主役にする。 |
| 階層に意味を持たせる | 🔶は章、🔷は章内の対象・テーマ。その中の確認・解説は①②③や太字のラベルにする。 |
| 出力の大きさに合わせる | 短い値は小さな表、大きな出力は表の外のコードブロック。長い全文は同じ場所の折りたたみへ。 |
| 一覧と詳細を併用する | 機能を用途別に探せるようにし、重要な項目は具体例と比較まで説明する。 |
| 根拠と完成物を確認する | 実測と説明例を区別し、保存後は見出しだけでなく内容・所属・出力・参照も確認する。 |

## 🔶 1. ページの目的・範囲・タイトルを決める

### 🔷 1-1. 「実験した順」ではなく「理解する順」に再編集する

学習中は、コードを試してからクラスを復習したり、結果を見て初めて設定の意味を調べたりします。その順番を、そのまま説明ページの順番にはしません。

本文では、読者がまだ知らない前提を先に補い、その後に具体的な処理と結果を置きます。「この変数はどこから来たのか」「何を準備すればこの処理になるのか」が、その場で分かるようにします。

### 🔷 1-2. 一つの学習単位を、一つのページにする

Tokenizer、Vocabulary、Tensor、Embeddingなど、後から独立して見返したくなる単位でページを分けます。実験フォルダは単位を考える参考になりますが、フォルダ名や実験番号をそのままページ名へ写す必要はありません。

関連する前提は数行で補い、詳しい内容は別ページへつなぎます。逆に、理解に不可欠な説明まで別ページへ追い出して、本文だけでは読めなくしないようにします。

### 🔷 1-3. タイトルは「何を理解するページか」で付ける

推奨する形は、**「対象名 ― 仕組みや役割の説明」**です。

| 避けたい例 | タイトルの例 |
|---|---|
| 002｜Tokenizerの実験 | Tokenizer ― 文章をトークンIDに変える仕組み |
| 実験004のまとめ | Tensor ― 数値の並びを形状・型・デバイスで扱う仕組み |
| 今回やったEmbedding | Embedding ― トークンIDをベクトルに変える仕組み |

実験番号をタイトルに付けません。ただし、本文の章番号は読み順を示すために使って構いません。

### 🔷 1-4. 本文に入れる情報と、外す情報

**入れるもの：** 対象の目的、仕組みを説明するコード、対応する結果、主要な機能・設定、疑問への回答、注意点、根拠となる資料。

**原則として外すもの：** `uv run`など単なる起動方法、フォルダを作る手順、端末を移動した経緯、コミット履歴、作業中の会話。

ただし、コンパイルや環境構築そのものが主題のページでは、コマンドが説明の中心になります。除外するのは「主題と無関係な操作手順」であり、コマンドを一律禁止するわけではありません。

学習ページの本文へ、「こうまとめると見やすい」「この記号を使う方針です」といった編集上の説明を混ぜません。そうした方針はこのガイドへ置き、学習ページには対象そのものの説明を残します。

## 🔶 2. 依存関係に沿って説明を並べる

### 🔷 2-1. 基本の読み順

```text
何のためにあるものか
    ↓
全体の中でどこを担当するか
    ↓
使うものを読み込む・指定する・準備する
    ↓
作成した対象の値・性質・出力の意味を同じ場所で確認する
    ↓
小さな例で一つずつ使い、各結果を読み解く
    ↓
機能・属性・設定を体系的に整理する
    ↓
条件による違い・注意点・関連概念を理解する
```

**オブジェクトを使う説明より、そのオブジェクトを作る説明を先に置きます。**

Tokenizerのページなら、次の順番が土台になります。

```text
AutoTokenizerを読み込む
    ↓
model_idを指定する
    ↓
from_pretrained()でtokenizerを準備する
    ↓
返ってきたものが何か確認する
    ↓
textを用意する
    ↓
tokenize()・encode()・decode()を使う
```

前提の準備は最初に一度説明し、以降の例では「上で作ったtokenizerとtextを使う」と明示して再利用します。すべての例へ同じ初期化コードを繰り返す必要はありません。

### 🔷 2-2. 章立てのひな型

| 順序 | 章の役割 | 含める内容 |
|---|---|---|
| 1 | 対象の全体像 | 何をするか、何はしないか、周辺の仕組みとの関係。 |
| 2 | 使うための前提と準備 | インポート、対象の指定、インスタンスやデータの準備。作成した対象の確認と、その結果の意味までを同じ節に置く。 |
| 3 | 基本の処理と結果 | 処理・結果の変数ごとに、コード・出力・性質・意味をまとめる。別の変換の結果は分ける。 |
| 4 | 機能を目的別に調べる | 主要メソッドや操作の一覧と、重要な項目の詳しい説明。 |
| 5 | 属性・設定の意味を深掘りする | 前半で見た値が、どの処理へ影響するかを説明する。オブジェクト全体の出力は繰り返さない。 |
| 6以降 | 主題固有の仕組み | 特殊トークン、形状変換、数値精度など、その主題で必要な内容。 |
| 最後 | 混同しやすい点とつながり | 対比表、理解の要点、関連ページ、公式資料。 |

章数は固定しません。短い主題ならまとめ、説明すべき対象が多い場合は分けます。Tokenizer固有の「Thinking」などを、無関係なページにも機械的に設けないでください。

### 🔷 2-3. 未定義の変数を、前半の例に先回りさせない

たとえば`tokenizer`を作る節では、まだ`text`を用意していないのに、実行すべきコードとして`tokenizer.tokenize(text)`を置きません。書き方の説明だけならインラインコードとして紹介し、実際の実行例は`text`を準備した後に置きます。

準備には二つの役割があります。何を読み込むかを理解することと、以降の例で再利用できる実物を用意することです。環境構築のコマンドを増やすのではなく、この依存関係を説明します。

## 🔶 3. 「処理ごとに分ける」と「同じ対象をまとめる」を両立する

### 🔷 3-1. 基本単位は、一つの理解対象

```text
対象・処理が分かる小見出し
    ↓
作成または変換のコード
    ↓
その対象を確認するコード
    ↓
直後に、対応する出力・処理結果
    ↓
同じ対象の性質と、結果の読み取り
```

**分ける単位はソースコードの一行でも、printの個数でもありません。対象と処理の意味で決めます。**

| 場面 | まとめ方 |
|---|---|
| `tokens`、`ids`、`decoded`をそれぞれ作る | 別の変換なので、それぞれのコード・結果・説明を分ける。 |
| 一つの`ids`の値・型・要素の型・要素数を調べる | 同じ対象の確認なので、一つのコードと対応する出力にまとめてよい。 |
| 一つの`gpu_tensor`の値・型・`device`・`dtype`・`shape`を調べる | 同じ対象の性質として同じ節へ集める。項目ごとに別章を作らない。 |
| 一つの`tokenizer`の型と巨大な全体表示を調べる | 同じ節の中で、型の確認と大きな表示を分けて配置する。大きさが違うからといって別の同格の節へ追い出さない。 |
| 同じ変数を途中で更新する | 更新前と更新後を明示する。別時点の値を一つの状態のように混ぜない。 |

**避ける両極端**

```text
分割しすぎ：
値を表示する章 → 型の章 → shapeの章 → 元の出力を説明する章

まとめすぎ：
tokenize・encode・decodeの全コード → 全出力を一括掲載

基本形：
対象Aの作成・確認・結果・解説
    ↓
対象Bの作成・確認・結果・解説
```

### 🔷 3-2. 同じ変数の確認は、コードと出力でも名前をそろえる

以下は、共有されたID列を使った**表示形式の例**です。Tokenizerの実行やGPU環境を新たに確認した記録ではありません。

**`ids`の中身・型・要素の型・個数を、一緒に確認する**

```python
ids = [89015, 5373, 133165, 126224, 35727, 94121, 128797]

print("ids:", ids)
print("type(ids):", type(ids))
print("type(ids[0]):", type(ids[0]))
print("len(ids):", len(ids))
```

**対応する出力**

```text
ids: [89015, 5373, 133165, 126224, 35727, 94121, 128797]
type(ids): <class 'list'>
type(ids[0]): <class 'int'>
len(ids): 7
```

**読み取り：** `ids`は7要素のリストで、要素は整数です。値だけを見せて型を別の場所へ送らず、何が入っている変数かをこの一組で確認します。

実際のTokenizerページでは、上のリスト代入に代えて、先に準備した`tokenizer`と`text`から`ids = tokenizer.encode(text)`で作る過程を示します。説明用の固定データと、本来の変換処理は混同しません。

### 🔷 3-3. 別の処理の結果は、直後にそれぞれ置く

`tokens = tokenizer.tokenize(text)`のコードの直後には`tokens`の出力を置きます。次に`ids = tokenizer.encode(text)`とその出力、続いて`decoded = tokenizer.decode(ids)`とその出力を置きます。

どれも同じ`tokenizer`を使っていても、得られる対象が違います。出力を一括で置いて読者に対応を探させません。全文のスクリプトを残す場合も、それだけで説明を済ませず、本文の個別対応を残します。

### 🔷 3-4. 出力がない処理は「何が変わったか」を書く

出力のない処理に架空の表示結果を付けません。また、説明を伴わない「なし」というコードブロックを毎回置く必要もありません。

| 処理の種類 | 結果の示し方 |
|---|---|
| インポート・単純な代入 | 利用可能になった名前、保存した値を説明する。必要なら確認用のprintを添える。 |
| インスタンスの読み込み | 返ってきたものを`type(...)`などで確認する。値の表示と、ダウンロード状況・警告のログを分ける。 |
| 設定の変更 | 変更前後を、対象の名前とともに示す。 |
| ファイル保存 | 保存先・生成ファイル・内容の変化など、確認できた結果を示す。 |
| 定義や擬似コード | 実行例ではなく、構造・仕組みの説明であることを明示する。 |

「代入自体は値を画面へ表示しない」と「読み込み中のログも一切出ない」は別です。実行状況によってログが出る処理まで、無条件に「画面出力なし」と断定しません。

### 🔷 3-5. 返り値・確認する式・画面表示を区別する

**`type(ids)`を調べ、その結果を表示する例**

```python
ids = [10, 20, 30]
kind = type(ids)
print(kind)
```

**対応する出力**

```text
<class 'list'>
```

`type(ids)`で得た値を`kind`が参照し、その値の文字列表現を`print(kind)`で表示しています。表の列名も「式の値」なのか「printした出力」なのかを区別します。

文字列の値を説明上`'right'`と表記することと、`print(...)`が`right`と表示することは同一の表記ではありません。実行結果の欄では、対応するコードの表示に合わせます。

## 🔶 4. 一つの変数・オブジェクトを、その場で理解できる形にする

### 🔷 4-1. 作成・確認・解説を、一つの親見出しへ集める

同じオブジェクトについて説明する内容は、別の同格の節に分散させません。

| 分散している構成 | まとめ直した構成 |
|---|---|
| 2-3で`tokenizer`を作成・表示し、2-4でその出力の意味を説明する。 | **2-3「tokenizer — 作成・出力・その意味」**の中へ、作成・型・全体表示・確認表・解説を集める。 |
| `tokens`の値を先に置き、後で「Python上の型」という節を作る。 | `tokens`を作った節で`type(tokens)`・`type(tokens[0])`・`len(tokens)`も確認する。 |
| Tensorの各性質をそれぞれ別テーマとして並べる。 | 同じTensorの確認として、`type`・`device`・`dtype`・`shape`・値をそろえる。 |

対象全体の初回確認は前半で完結させます。後半で属性を詳しく解説する場合は、「先ほどの値が何を意味し、どの処理に影響するか」を扱い、同じ全体出力をもう一度掲載するだけにしません。

### 🔷 4-2. 日本語の説明より、確認するコード表現を見つけやすくする

| 単独では分かりにくいラベル | 主役にする式・表示コード | 添える説明 |
|---|---|---|
| 型 | `type(tokenizer)` | どのクラスのインスタンスか。 |
| 読み込み元 | `tokenizer.name_or_path` | 設定を読み込んだ場所。 |
| 形状 | `tensor.shape` | 次元ごとの要素数。 |
| デバイス | `gpu_tensor.device` | データを置いている計算先。 |
| データ型 | `gpu_tensor.dtype` | 要素を表現する型。 |
| 全体の表示 | `print(tokenizer)` | オブジェクトの文字列表現を表示する。 |

これはラベルの付け方の例です。使える式は、対象のクラスとAPIに合わせて選びます。全オブジェクトに同じ属性があるとは扱いません。

日本語の説明は不要という意味ではありません。**実際に確認する式を先に見せ、その横や下へ意味を添えます。** 入力に誤記があっても、そのまま存在しないAPIとして残しません。たとえば型の確認は`type(...)`とし、`style(...)`という別の名前へ置き換えません。

作成時に重要だった`type(tokenizer)`を、後の確認表から落とさないでください。コード、対応する出力、表を設ける場合の該当行が、同じ対象を指していることを確認します。

### 🔷 4-3. 大きなprint出力を、表へ押し込まない

**一つの対象をまとめることと、一つの表へすべてを入れることは違います。**

```text
🔷 2-3. tokenizer — 作成・出力・その意味
    ① 作成する
       作成コード → 処理結果

    ② type(tokenizer)
       確認コード → 型の出力

    ③ print(tokenizer)
       表示コード → 出力の主要部分
                      └─ 同じ出力の全文を開く折りたたみ

    ④ 同じtokenizerの確認式と値
       type(tokenizer)・属性・IDなどの短い値を表にする

    ⑤ この出力を読み解く
       作成・返り値・設定の意味を説明する
       言語の復習は、必要ならここに補足として置く
```

長い出力は表の外のコードブロックに置きます。通常表示する主要部分を残し、**すぐ下にその出力全文の折りたたみ**を置きます。全文を後半の別章へ送り、読者に探させません。

抜粋には「抜粋」、改行を整えたものには「改行を整理」と明記します。「全文」と表示する欄には、掲載対象の出力を省略せず残します。折りたたみの名前も「詳細」だけにせず、「③の出力全文：print(tokenizer)」など、何に属するものかを示します。

全体表示は、そのオブジェクトが提供する文字列表現であり、全メモリや全属性を必ず網羅する表示とは限りません。「出力全文」と「オブジェクトの全情報」を混同しないように説明します。

### 🔷 4-4. 短い結果は、確認する式と対応する小さな表にする

表の基本形は「確認する式／値／意味」です。`type(tokenizer)`の完全な出力がすぐ上にある場合、表ではクラス名を短く書いても構いませんが、省略であることと完全な表示の場所が分かるようにします。

表に載せる値が、個別に実行した結果なのか、既に表示されたオブジェクトの出力から整理した値なのかも区別します。後者を、新しく全項目を実行した記録のようには書きません。

大きな文字列、Tensor、辞書などは表の外へ置き、短い確認値は同じ節の表へ置きます。表示方法が違っても、所属する変数・オブジェクトは同じです。

### 🔷 4-5. まとめすぎず、必要な性質を選ぶ

単純な文字列に巨大なプロフィール表を作る必要はありません。数行で分かるなら、作成コードと`print`・`type`・`len`の確認を一組にすれば十分です。

複雑なオブジェクトでは、読み込み元・型・要素数・形状・データ型・配置先など、今回の仕組みの理解につながる性質を選びます。意味が説明されない属性を大量に追加することは避けます。

異なる対象を横に並べる比較表は、最後の整理として有効です。ただし、各対象の作成・確認・解説がばらばらなまま、比較表を追加しただけで修正完了にはしません。

## 🔶 5. 一覧は「項目数」より「探せること・理解できること」を重視する

### 🔷 5-1. 表が向く場所と、文章が向く場所を分ける

| 説明したいこと | 適した見せ方 |
|---|---|
| 用語・役割・値を比較したい | 表 |
| 入力から出力への変化を追いたい | 処理の流れ＋コードと結果 |
| なぜそうなるかを説明したい | 小見出し＋短い段落 |
| 似た機能を選び分けたい | 比較表＋それぞれの具体例 |
| 多数のメソッド・記号を探したい | 用途別の一覧＋重要項目の詳細 |
| 長い生の出力・前提の復習を残したい | 折りたたみ |

**表を増やすこと自体を目的にしません。** 長文を表のセルに押し込むだけなら、小見出しと段落へ分けた方が適切です。

### 🔷 5-2. メソッドは「用途別一覧＋個別説明」にする

対象クラスの機能を整理するときは、今回使った数個だけに勝手に限定しません。継承して利用できるものも含め、主題に関係する公開メソッドをできるだけ拾い、読み込み・変換・参照・変更・保存などの目的で分類します。

ただし、内部実装用のメソッド、重複する別名、バージョン限定の旧APIを無差別に並べて「完全な一覧」とは呼びません。掲載範囲と、必要なら確認した版を示します。

一覧だけで理解が完結しない重要項目は、直下に個別説明を付けます。

| 個別説明で答える問い | 書く内容 |
|---|---|
| 何のために使うか | 解決する目的・使う場面。 |
| 何を渡すか | 入力値・型・前提になる設定。 |
| 何が返るか | 戻り値の型、内容、対象自身への変更の有無。 |
| 具体的にどうなるか | 小さなコードと、その直後の出力・結果。 |
| 似たものと何が違うか | 選び分け、入力や戻り値の違い。 |
| 何に注意するか | 条件、制限、バージョン差、副作用。 |

たとえばTokenizerでは、encodeとオブジェクト自体の呼び出し、decodeとbatch_decode、decodeとconvert_ids_to_tokensを比較する、といった整理が候補になります。

**重要な比較を「まだ試していないので一覧だけ」にして、説明を先送りしないでください。** 説明に必要なら追加例を用意し、未実行なら「仕様に基づく出力例」と明示します。曖昧な結果は断定せず、確認してから載せます。

### 🔷 5-3. メソッド・属性・引数は別に整理する

| 分類 | 一覧に載せる観点 |
|---|---|
| メソッド・関数 | 目的、入力、戻り値、状態変化。 |
| 属性・プロパティ | 名前、意味、今回の値、どこで使われるか。 |
| 呼び出し時の引数 | 名前、指定例、既定値、指定すると何が変わるか。 |
| クラス・インスタンス | 誰が生成するか、何が返るか、どの実物が処理を行うか。 |

機能一覧では種類を分けます。ただし、一つのオブジェクトの確認欄で関数・属性・表示コードを一緒に扱うこと自体は禁止しません。その場合は「確認する式・表示コード」と明示し、それぞれ何をするかを説明します。分類のために、同じ対象の確認を遠くへ分散させないでください。

### 🔷 5-4. 多数の記号・特殊トークンなどは、省略しすぎない

Tokenizerで表示された追加トークンのように、具体的な項目群を説明する依頼では、重要な項目を「など」だけでまとめません。

種類ごとに分類し、各項目が確認できるようにします。開始・終了の対は同じ行にまとめても構いませんが、両方の名前・ID・役割が対応するように書きます。

共通のフラグは一か所で説明し、各項目には固有の意味や注意点を残します。単なる名前の一覧でも、同じ説明の繰り返しでもない構成にします。

属性の名称だけを並べる場合も、所有する対象が分かるようにします。たとえば説明の途中で単に`dtype`とするより、最初に`gpu_tensor.dtype`と示す方が、どの変数の性質かを追いやすくなります。

## 🔶 7. 正確さと具体性を両立させる

### 🔷 7-1. 情報の種類を区別する

| 種類 | 表示の例・扱い |
|---|---|
| ユーザーが共有した実測 | 「今回の出力」「共有された結果」。入力・コードとの対応を保つ。 |

| 確認項目を加えた再構成例 | 元の値へ型・個数・表示ラベルなどを加えた例。元の実行ログそのものとは区別する。 |

### 🔷 7-2. 個別の結果を、一般仕様に広げすぎない

一つのTokenizerでのID、一つのモデルの設定、一度のGPU実行の成功などは、それぞれの条件で確認した事実として書きます。

「この例ではこうだった」と「常にこうなる」を分けます。以前の会話や既存ページに不正確な説明があれば、見た目の統一のために残さず、根拠を確認して直します。

### 🔷 7-3. 根拠を追えるようにする

API・モデル仕様・挙動の説明には、適切な公式ドキュメント、配布設定、実装などを確認し、根拠の近くにリンクを置きます。バージョンによって変わる内容は、必要に応じて対象の版やモデルのrevisionを添えます。

参考資料を末尾にまとめるだけでなく、「どの説明の根拠か」が分かるようにします。古い会話の断言や、参考ページの記載だけを理由に、現行仕様と決めつけないでください。

乱数、処理時間、生成文章、オブジェクトのアドレスなどは、そのまま同じ値が再現すると説明しません。GPU向けの例では、手元で未確認のCUDA出力を実測と見せず、必要な実行条件と例の位置づけを示します。

同じ文章を使い続けても、確認する単位が違う場合があります。文字列の長さ、トークン数、配列の形状などを同じ意味の数値として並べないようにします。

## 🔶 8. 記号・見出し・水平線で、所属と階層を表す

### 🔷 8-1. 記号の色は、実際の階層に対応させる

基本の階層は次の3段階です。このガイドも同じ見出し規則を使っています。

| 階層 | 表示方法 | 内容の単位 |
|---|---|---|
| 大きな章 | `## 🔶 2. Tokenizerを準備する` | 全体の一段階・大きなテーマ。 |
| 章内の対象・テーマ | `### 🔷 2-3. tokenizer — 作成・出力・その意味` | 一つのオブジェクト、一つの結果、独立して扱う機能群。 |
| 同じ対象の確認・解説 | 太字の`① 作成`、`② type(tokenizer)`、`③ print(tokenizer)`など | 親見出し内で完結する作業・観察・説明。新たな同格の節にしない。 |

**🔶と🔷は飾りではありません。色と見出しの大きさで、親子関係を示します。** 同じ階層の兄弟には同じ記号を使い、別の色を付けるためだけに階層を増やしません。

最下層では記号をさらに増やすより、①②③や短い太字ラベルを使います。深い見出しを大量に作ったり、🔷と🔹の大きさの差だけで別階層を表したりしません。番号と見出し名も併用し、色だけに依存しない形にします。

### 🔷 8-2. 同じ出力の説明を、別の兄弟見出しにしない

次は**構成の比較**です。実行コードではありません。

```text
避けたい構成
🔷 2-3. tokenizerを作成して表示する
🔷 2-4. そのtokenizerの出力の意味を説明する

まとめ直した構成
🔷 2-3. tokenizer — 作成・出力・その意味
    ① 作成
    ② type(tokenizer)
    ③ print(tokenizer)
    ④ 同じtokenizerの確認式と値
    ⑤ その出力を読み解く
```

同じ対象の説明を統合するのであって、「2-4をオレンジにする」だけでは解決しません。まず内容の親子関係を直し、その構造に記号を対応させます。

一方、`AutoTokenizer`の読み込み、`model_id`の指定、`tokenizer`の取得は、準備の中で異なる対象を扱うため、兄弟の小見出しにできます。

### 🔷 8-3. 水平線は大きな境目に置く

水平線は、原則として章の境目に置きます。同じ対象の作成コードと出力の間や、出力とその解説の間には置きません。

対象が変わる場所は🔷の小見出しで示します。各printの間に水平線を追加して、同じ系列の観察がばらばらに見えないようにします。

### 🔷 8-4. コールアウトの色は、見出しとは別の役割にする

| 色 | コールアウトでの用途 |
|---|---|
| 青系 | 中心概念、全体像、仕組みの要点。 |
| 緑系 | 出力から確認できること、理解のまとめ。 |
| 黄系 | 混同しやすい点、例外、重要な注意。 |

見出しの🔶・🔷は**階層**、コールアウトの色は**内容の性格**を示します。この二つの役割を混ぜません。通常の本文は無色を基本とし、確認項目のすべてを色付きの大きな枠に入れないようにします。

### 🔷 8-5. 折りたたみも、親との関係を保つ

長い出力全文、言語の復習、詳細な内部実装、参考資料は折りたたみにできます。

主要な作成手順、`type(...)`の確認、出力の主要部分、重要な比較は通常表示します。長い出力全文の折りたたみは、対応する表示コードと抜粋のすぐ下です。復習欄も、その復習が必要になった対象の下に置きます。

「詳細」「補足」だけでなく、「③の出力全文：print(tokenizer)」「この返り値を理解するためのPython復習」など、所属が分かる名前を付けます。

### 🔷 8-6. 読みやすさを、情報の距離で確認する

見出しだけを読んでも、大きな流れと、各対象が属する章を追えるようにします。細かい項目を増やす前に、読者が同じ変数の情報を何度も探し直していないかを確認します。

表のセルには短い比較可能な値を置き、長い出力や長文の理由は外へ出します。狭い画面でも追える縦方向の構成を基本にし、複雑な多段の横並びは避けます。

一つの表に入れられない情報でも、同じ小見出し内にあれば一つのまとまりにできます。逆に表を増やしても、同じ対象の情報が散らばったままなら整理されたことにはなりません。

## 🔶 9. Notionへ作成・修正するときの進め方

### 🔷 9-1. 書く前に、現在のページと依存関係を確認する

指定された親ページ、セクション、対象ページを実際に読みます。参照ページがある場合は、その配色・見出し・表・補足の使い方を確認します。ただし、参考ページの不備まで模倣しません。

対象範囲と章立てを決め、主役になる変数・オブジェクトを特定します。各対象について、作成コード、確認式、実際の出力、解説がどこへ入るかを先に決めます。

ユーザーと修正案に合意した場合は、約束を実際の配置に落とし込みます。名前や章数を合わせるだけでなく、「全文をどこへ置くか」「どの確認を一緒にするか」まで確認します。

### 🔷 9-2. 局所修正と再構成を使い分ける

一か所の誤字なら局所修正で済ませます。全体の見直しが求められた場合や、修正の積み重ねで所属・重複が崩れた場合は、章を足し続けず、親子関係から整理し直します。

**残すもの：** 既に理解できた説明、実測結果、必要な機能・設定の解説、重要な比較、根拠のリンク、既存の子ページや参照。

**整理するもの：** 重複した全体出力、同じ対象の解説を分けた兄弟見出し、別の場所へ移動したままの古い文章、名称だけ変えて残った不要な項目。

一つの依頼を直すために、以前に合意した条件を失わないようにします。たとえば出力をまとめる修正で`type(tokenizer)`を消したり、階層を変える修正で準備を後ろへ戻したりしません。

### 🔷 9-3. 保存時に、コードと文字を壊さない

Notionへ書き込む方法の書式を確認します。Markdownのコードフェンス、表内の縦棒、特殊トークンの山括弧、折りたたみの入れ子などを正しく扱います。

`self.name`や`tensor.shape`などはインラインコードで記し、意図しないWebリンクに変わっていないか確認します。太字とインラインコードを組み合わせた箇所も、余計な記号が露出していないか見直します。

本文の一括置換に使う記号が、出力の実データにも含まれていないか確認します。たとえば内部トークン表現中の`§`を、コードのバッククォート用の仮記号として一括変換すると、結果を壊します。コードやデータは必要のない変換をしないことが基本です。

通常のMarkdownファイルと、Notionの編集機能が受け付ける書式は同一と決めつけません。このガイドとひな型は通常のMarkdownで、Notion上の色・コールアウト・折りたたみは、利用する編集方法に合わせて反映します。

### 🔷 9-4. 保存後に、見出しから出力まで読み直す

保存後のページを再取得し、前半だけでなくページ全体を確認します。出力確認の抜粋しか読めていない場合は、残りも読みます。

| 合意した修正 | 完了の判断基準 |
|---|---|
| 準備を先に置く | 初めて使う前に、クラス・変数・対象の準備が分かる。 |
| 同じ対象をまとめる | 作成・値・型・性質・出力の意味が同じ親見出しの中にある。 |
| 別の処理を分ける | 各変換の直後に、その変換の結果があり、別の出力と混ざっていない。 |
| 確認する式を見せる | `type(...)`や所有する変数を含む属性名が、ラベルや表から欠落していない。 |
| 大きな出力を残す | 表の外に主要部分があり、そのすぐ下で全文を開ける。 |
| 階層を明確にする | 🔶・🔷・①②③が実際の親子関係に対応し、同じ出力の説明が別の兄弟節にない。 |
| 詳しい機能を整理する | 用途別の一覧だけでなく、必要な個別説明・入力・返り値・比較・具体例がある。 |
| 重複を減らす | 説明を失わず、繰り返しの全体表示や古い参照が整理されている。 |

章を統合・移動したら、目次、番号、本文の「第○章」「2-4」なども更新します。参照先がなくなった番号を残しません。

確認できたのが本文構造だけなら、画面上のレイアウトを完全に検証したとは報告しません。実際に変更・確認できた内容を、短く具体的に伝えます。
